# PHASE 12.1 — PRIVATE-ALPHA SIGNING IDENTITY (TASK B)

Guide reference: `THRAKSHA_DEMO_IMPLEMENTATION_PHASE_12_1_RC2` §§10–17.

## 1. What RC1 did, and why it had to change

RC1 was signed with the Android SDK's standard debug key:

| Field | RC1 value |
| --- | --- |
| Signer | `C=US, O=Android, CN=Android Debug` |
| Certificate SHA-256 | `2a7c7cf3fa6214329168e2037d8a6ecdd92f5e7ab981f439d291ebccac3a19d4` |
| Schemes | v2 only |

Two consequences, both real:

1. **The debug private key is not secret.** It ships with the Android SDK on every
   developer machine. Anyone can produce an APK the device will accept as an update to an
   RC1 install.
2. **No upgrade path.** Android identifies an installed app by package name *plus* signing
   certificate and refuses an update whose signer differs. A properly-signed build cannot
   update an RC1 install; RC1 must be uninstalled first.

RC2 replaces this with a dedicated Thraksha signing identity under the owner's custody.

## 2. Signing configuration — implemented (no credentials, no key)

`app/build.gradle.kts` now resolves release credentials from untracked sources at build
time. No secret, password, path or key material appears in any tracked file.

### Credential resolution order

1. `keystore.properties` at the repository root — **git-ignored** (`.gitignore` line 30),
   never committed.
2. Environment variables, as a fallback:
   `THRAKSHA_KEYSTORE_FILE`, `THRAKSHA_KEYSTORE_PASSWORD`,
   `THRAKSHA_KEY_ALIAS`, `THRAKSHA_KEY_PASSWORD`.

A tracked, value-free `keystore.properties.template` documents the format.

### Keystore location is enforced, not merely requested

Guide §13 requires the keystore live outside the repository. The build **fails at
configuration time** if `storeFile` resolves to a path inside `rootDir`:

```
Release keystore is inside the repository at <path>. Move it to a private directory
outside <repo> and update keystore.properties.
```

A keystore under the project tree is one `git add -f` away from being published
permanently, so this is a check rather than a comment.

### No silent debug fallback — verified

`buildTypes.release.signingConfig` is the `privateAlpha` config when credentials resolve,
and **`null`** otherwise. AGP would normally respond to a null signing config by quietly
emitting `app-release-unsigned.apk`, which reads as success in a build log and is not. A
hard gate on `packageRelease` / `assembleRelease` / `bundleRelease` prevents that.

Verified by running `:app:assembleRelease` with no credentials present:

```
* What went wrong:
Execution failed for task ':app:packageRelease'.
> Release signing credentials are not configured — refusing to build.

  Missing: storeFile / THRAKSHA_KEYSTORE_FILE, storePassword / THRAKSHA_KEYSTORE_PASSWORD,
           keyAlias / THRAKSHA_KEY_ALIAS, keyPassword / THRAKSHA_KEY_PASSWORD
  ...
  There is NO debug-key fallback by design.

BUILD FAILED
```

`app/build/outputs/apk/release/` was confirmed absent afterwards — no unsigned artifact was
produced. Debug builds and the unit suite are unaffected by the gate (the check runs at
execution time, not configuration time): `:app:assembleDebug :app:testDebugUnitTest`
succeeded, 213 unit tests, 0 failures.

### Signature schemes configured

| Scheme | Enabled | Reason |
| --- | --- | --- |
| v1 (JAR) | no | minSdk 26 does not need it; it slows install and adds no security. |
| v2 | yes | The baseline for API 24+. |

## 4. ⚠ KEY CONTINUITY — DO NOT LOSE THIS KEY

> **Every future Thraksha private-alpha update must be signed with this same key.**

Android identifies an installed app by *(package name + signing certificate)*. If the
keystore or its passwords are lost:

* no future build can update an existing install;
* the app must be uninstalled and reinstalled fresh;
* uninstalling destroys the SQLCipher-encrypted database and the hash-chained audit log on
  that device — that history is not recoverable.

Therefore:

* keep **at least one backup** of the `.jks` and its passwords **outside** the development
  laptop and **outside** this repository;
* store the passwords in a password manager, not in a note beside the keystore;
* **do not rotate casually.** Rotation without v3 rotation lineage means every installed
  user must uninstall and lose their data.

## 5. Key creation — owner action

Per guide §11, the permanent keystore is created and stored by the owner, not by the build
and not by Claude. Suggested creation command, for the owner to run and adjust (never with
the password on the command line where it would land in shell history — `keytool` will
prompt):

`keytool` on this machine is at `C:\Program Files\Java\jdk-20\bin\keytool.exe` (JDK 20).

PowerShell:

```powershell
New-Item -ItemType Directory -Force C:\Users\kplee\secure\thraksha

& "C:\Program Files\Java\jdk-20\bin\keytool.exe" -genkeypair -v `
  -keystore C:\Users\kplee\secure\thraksha\thraksha-private-alpha.jks `
  -storetype PKCS12 `
  -keyalg RSA -keysize 4096 -validity 10950 `
  -alias thraksha-private-alpha
```

`keytool` prompts for the passwords and for the certificate subject (CN/OU/O/L/ST/C).
Passwords are **not** passed on the command line, so they never reach shell history.

The subject you enter becomes the permanent public identity of every Thraksha
private-alpha build. Something like `CN=Thraksha Guardian, O=Thraksha, C=IN` is
appropriate. It must not be `CN=Android Debug` (guide §16).

`-validity 10950` is 30 years; a private-alpha key that expires mid-life would strand
existing installs. PKCS12 is the modern keystore format (legacy JKS triggers a migration
warning). RSA 4096 rather than 2048 because this key has a 30-year horizon.
