Real-World Malware Intelligence for Thraksha: Sourcing,
Licensing, Schema, and Integration
TL;DR
Build Thraksha's real-intelligence corpus on abuse.ch — MalwareBazaar (APK SHA-256 hashes + the
Code Signing Certiﬁcate Blocklist), ThreatFox (Android apk.* family IOCs), and URLhaus (malware-
distribution URLs) — because these are the only reputable free-to-query sources that cover Android
speciﬁcally and expose the exact indicator types Thraksha matches. Do NOT build on VirusTotal's public
API: its terms forbid commercial products and substitute-AV use.
The single biggest risk is licensing, not technology. abuse.ch data is free to query under "fair use / non-
commercial" terms, but its published terms are effectively silent on redistributing indicators to your users
inside a signed ThreatPack — so bundling and shipping those indicators is a LEGAL / LICENSINGREVIEW REQUIRED item that must be resolved in writing with Spamhaus/abuse.ch before any
commercial/investor build.
For Android, trust APK SHA-256 and malicious signing-certiﬁcate ﬁngerprints as strong indicators;
treat package names, IPs, and URLs as weak, expiring contextual evidence. Ship a small oﬄine pack (a
few thousand indicators, well under 1 MB) and make the demo about scanning real apps against real
intelligence and honestly reporting zero matches, plus a controlled VillainCaller detection — not about
forcing malware onto a clean phone.
Key Findings
1. abuse.ch is the backbone. MalwareBazaar (malware sample hashes incl. APKs), ThreatFox (multi-typeIOCs incl. apk.* families), URLhaus (malware-distribution URLs), and SSLBL (malicious TLS certs/JA3)
are all free-to-query under abuse.ch "fair use" principles, now operated in partnership with Spamhaus.
They cover exactly the indicator types Thraksha inspects.
2. abuse.ch now requires a free Auth-Key (from auth.abuse.ch) for API and export access, and enforces
fair-use rate limits; commercial/for-proﬁt use, per the ThreatFox Community API page, "may require a
paid subscription for the enhanced abuse.ch commercial API."
3. ThreatFox explicitly expires IOCs older than 6 months (since 2025-05-01) to avoid false positives,
"mostly happening on cloud based infrastructure where assets (e.g. IP addresses) are changing
customers quickly" — a policy Thraksha should mirror.
4. A dedicated Code Signing Certiﬁcate Blocklist (CSCB) exists on MalwareBazaar (SHA-256 thumbprints,
issuer/subject CN, serial, bl_reason = malware family). This maps directly to Thraksha's signing-
certiﬁcate ﬁngerprinting capability.
5. VirusTotal's public API is off-limits for Thraksha's use case: it "must not be used in commercial productsor services. It can not be used as a substitute for antivirus products and it can not be integrated in any
project that may harm the antivirus industry directly or indirectly," with "immediate permanent ban" for
non-compliance. Its Enterprise agreement also forbids sublicensing/redistribution of any Samples,
datafeed, or metadata.
6. AndroZoo (University of Luxembourg) is the best Android-speciﬁc research corpus — "approximately 24
million APK ﬁles" per its MSR 2024 retrospective, each keyed by SHA-256 with SHA-1/MD5, market,
signing cert, and per-AV labels — but its access conditions prohibit redistribution and commercial use
and require a faculty/permanent-position sponsor. Usable for internal research/curation only, not for
shipping, and likely unavailable to a solo non-academic developer.

7. Android indicator reliability: APK SHA-256 and malicious signer certs are strong; package names are
weak (spoofable/reused); network IOCs (IP/domain/URL) decay fast and suffer from shared-
hosting/CDN false positives.
Details
What Thraksha Needs From Threat Intelligence
Thraksha's scanner inspects: package identity, signing-certiﬁcate SHA-256, base-APK SHA-256,
permissions/proﬁle, and network destinations. The IOC feed therefore needs, in priority order: (1) APK SHA-
256 hashes with malware-family labels; (2) malicious signing-certiﬁcate ﬁngerprints; (3) malicious domains
/ IPs / IP:port / URLs for network-destination analysis; and (4) rich metadata (family, ﬁrst/last seen,
conﬁdence, source) so PolicyEngine can reason rather than blindly quarantine. Package names are usefulonly in combination with a hash or signer.

Detailed Review of Each Source
MalwareBazaar (abuse.ch/Spamhaus). Purpose: sharing conﬁrmed malware samples ("over 1'120'404
conﬁrmed malware samples" per the FAQ; "Over 500 daily consumers"; "around 100 million API requests in 30
days," Oct 2024). Provides SHA-256/SHA-1/MD5, imphash/tlsh/telfhash/gimphash, signature (family), tags
(including apk/android), ﬁrst_seen, and a Code Signing Certiﬁcate Blocklist (CSCB) — code-signing certs
dumped by ReversingLabs' A1000 platform and manually vetted by abuse.ch — with SHA-256 thumbprint,
issuer/subject CN, serial number, validity, and cscb_reason/bl_reason (family, e.g. "CobaltStrike,"
"Quakbot"). Access: REST API (mb-api.abuse.ch), bulk CSV/hash exports, hourly/daily batches, and daily
MISP events. Auth: free Auth-Key required. The ﬁle-download API is limited to 2,000 samples/IP/day
(irrelevant to Thraksha, which never downloads binaries). Update cadence: recent exports every 5 min, full
dumps hourly. MalwareBazaar Quality is high (conﬁrmed malware only; no adware/PUP). MalwareBazaar For
Thraksha, use the hash-list exports and the CSCB CSV (/export/csv/cscb/) — metadata only, never the
sample ZIPs (password infected).
ThreatFox (abuse.ch/Spamhaus). Purpose: sharing IOCs associated with malware ("over 1'808'084 IOCs").IOC types include sha256_hash, domain, ip:port, url, and more; each carries a malware family
(including Android families apk.anatsa [aka ReBot/TeaBot/Toddler], apk.hydra, apk.888_rat,
apk.irata, apk.smsspy, apk.doublelocker), a submitter-chosen conﬁdence level (abuse.ch warns to
"only use high conﬁdence levels on IOCs you have manually vetted"), ﬁrst/last seen, and reporter/reference.
There is an "Android" tag. Access: REST API (threatfox-api.abuse.ch/api/v1/), data export (CSV/JSON),
host-ﬁle and Suricata/RPZ formats, and a MISP event feed. Auth: free Auth-Key.IOCs older than 6 months
are expired and dropped from API/export (still visible in UI). Abuse No STIX/TAXII — abuse.ch dropped it
because the export grew to gigabytes. This is Thraksha's richest single source for Android network + hash
IOCs with family labels.
URLhaus (abuse.ch/Spamhaus). Malicious URLs used for malware distribution, URLhaus with associated
payload hashes (incl. SHA-256), host, status (online/oﬄine), tags, and timestamps ("Over 5000 daily
consumers"). Access: REST API, full/active/recent database dumps (CSV/JSON, every 5 min), and MISP daily
feed. Note the ISP/CERT country/ASN/TLD feeds are explicitly "not intended for blocklisting… nor for beingused as an Indicator Of Compromise" — use the API datasets, not those feeds. URLs disappear fast; treat as
short-lived.
SSLBL (abuse.ch). Malicious SSL certiﬁcates (SHA-1 ﬁngerprints) and JA3 ﬁngerprints tied to botnet C2, plus
a botnet C2 IP blocklist. abuse.ch itself warns the JA3 list is "not tested against known good traﬃc yet and
may cause a signiﬁcant amount of FPs," and the IP RPZ contains only IPs seen in the past 30 days. Low direct
Android relevance; optional network enrichment only.
AndroZoo (University of Luxembourg). The premier academic Android corpus — "approximately 24 million

Licensing / Redistribution Analysis
The locked constraint — an oﬄine signed ThreatPack embedded in the APK, redistributed to every user, in aproduct intended for an investor demo and eventual commercial sale — is exactly the case where "free to
query" ≠ "free to redistribute." Applying the A–G test:
abuse.ch (MalwareBazaar/ThreatFox/URLhaus/SSLBL):
A. Query privately — Yes, under fair use with a free Auth-Key.
B. Store internally — Yes (implied by fair-use querying).
C. Normalize into Thraksha's schema — Not addressed in the published terms →  REVIEW REQUIRED
(likely acceptable as internal processing).
D. Embed a subset in an oﬄine demo pack — Not explicitly permitted →  LEGAL / LICENSING
REVIEW REQUIRED.
E. Redistribute indicators to users — Not explicitly permitted →  LEGAL / LICENSING REVIEW
REQUIRED. The reachable abuse.ch terms speak only to query volume and commercial vs. non-
commercial use, and are silent on redistribution to third parties/end users.
F. Commercial product use — abuse.ch states commercial/for-proﬁt use "may require a paidsubscription" via Spamhaus →  for anything beyond a personal/non-proﬁt demo, obtain the
Spamhaus commercial arrangement in writing.

Android Indicator Reliability Analysis
APK SHA-256 — STRONG but brittle. An exact base-APK SHA-256 match is high-conﬁdence proof that a
speciﬁc known-bad artifact is present, with essentially zero false positives. The weakness is coverage:
Android malware is heavily repackaged and rebuilt, so any code change, re-signing, or resource tweak yields a
completely different hash (a large body of research conﬁrms repackaging is the dominant malware-
distribution technique). Split APKs (App Bundles) mean the base-APK hash differs from what a store served.
Recommendation: trust an APK SHA-256 match as a "KNOWN THREAT MATCH," but never rely on hashes
alone for coverage — pair with signer-cert matching.
Signing-certiﬁcate ﬁngerprints — STRONG for campaigns. Because repackaged/rebuilt malware within onecampaign is frequently signed by the same threat-actor key, a malicious signer ﬁngerprint catches many hash
variants at once — Thraksha's highest-leverage Android indicator. Caveats: (1) stolen/leaked platform
certiﬁcates exist — the Nov 2022 Android Partner Vulnerability Initiative (APVI) disclosure by Google reverse
engineer Łukasz Siewierski showed platform certiﬁcates belonging to Samsung, LG, Revoview, and Mediatek
being used to sign Android malware (Google advised affected vendors to "rotate the platform certiﬁcate by
replacing it with a new set of public and private keys"), so a compromised cert can appear on both good and
bad apps — match on the malware-associated cert, not the vendor's legitimate current cert; (2) shared
debug/test keys (the public AOSP test keys) cause false positives — maintain an allowlist of well-known
debug/test certiﬁcate ﬁngerprints and never quarantine on those; (3) Android v2/v3 signing and key rotation
(SigningInfo signing history) mean an app can present multiple certs — evaluate the full signing lineage.
Recommendation: treat a vetted malicious-signer match as strong evidence, second only to a hash match,
guarded by a debug/test-key allowlist.
Package names — WEAK. Package IDs are trivially spoofable and reusable; benign and malicious apps canshare names, and malware rotates package names freely. A package-name match alone must never trigger
containment. Recommendation: use it only as a corroborating signal with a signer or hash match, or to raise
"SUSPICIOUS / REVIEW."
Domains / IPs / URLs — WEAK and time-decaying. Fast-ﬂux, cloud, CDN, and shared hosting mean a
malicious IP today is a benign SaaS tenant next week; domains change ownership; URLs vanish. abuse.ch's
own 6-month IOC expiry and 30-day IP RPZ windows codify this. Recommendation: use network IOCs only for

the network-destination analysis (contextual evidence / "HIGH-CONFIDENCE IOC MATCH" at best when fresh
and corroborated), with aggressive expiry.
Recommended Thraksha IOC Schema
Normalized record (JSON canonical form; stored on-device in a compact binary/SQLite form):
indicatorId        (string, UUID)                         — MANDATORY
indicatorType      (enum)                                 — MANDATORYindicatorValue     (string, canonicalized)                — MANDATORYplatform           (enum: android|windows|cross|network)  — MANDATORY
classification     (enum: malware|c2|distribution|phishing|pua|suspicious) — MANDATORYmalwareFamily      (string, normalized, e.g. "anatsa")    — optionalseverity           (enum: low|medium|high|critical)       — MANDATORY
confidence         (int 0–100, source-declared)           — MANDATORYsource             (enum: malwarebazaar|threatfox|urlhaus|sslbl|internal) — MANDATORYsourceReference    (string/URL to origin record)          — MANDATORY (provenance)
firstSeen          (ISO-8601 UTC)                          — optionallastSeen           (ISO-8601 UTC)                          — optionalexpiresAt          (ISO-8601 UTC)                          — MANDATORY
revoked            (bool, default false)                   — MANDATORYenabled            (bool, default true)                    — MANDATORYtags               (array<string>)                         — optional
license            (enum/string, e.g. "abuse.ch-fairuse")  — MANDATORYattribution        (string, display credit)                — optionalmetadata           (object, free-form)                     — optional
Enums for indicatorType:apk_sha256, cert_sha256, cert_sha1, package_name, domain, ipv4,
ipv6, ip_port, url, ja3.
Validation & canonicalization rules:
SHA-256: lowercase hex, exactly 64 chars, ^[0-9a-f]{64}$. Normalize uppercase.
Certiﬁcate ﬁngerprint: lowercase hex, no colons/separators, algorithm recorded separately
(cert_sha256 = 64 hex; cert_sha1 = 40 hex). Store issuer/subject CN and serial in metadata.
Domain: lowercase, IDNA/punycode-normalized, trailing dot stripped, no scheme.
IPv4/IPv6: normalized (IPv6 lowercased, zero-compressed); ip_port stored as ip|port.
URL: scheme+host lowercased, host punycode-normalized, fragment stripped; path/query kept verbatim.
package_name: validated against the Android package regex; always low-trust.
Deduplication: natural key = (indicatorType, canonical indicatorValue). On collision, merge sources
into a sources[] list and keep max severity + max conﬁdence + earliest ﬁrstSeen + latest lastSeen. This
is what enables corroboration counting.
Conﬁdence / Source Trust Model
Do not present conﬁdence as an ML probability. Use a deterministic, explainable tiering:
Source trust level (Thraksha-assigned): MalwareBazaar/ThreatFox = High; URLhaus = High for URLs;
SSLBL/JA3 = Medium (FP-prone); OTX = Medium; internal demo indicators = labeled Demo.
Indicator-type strength:apk_sha256 & cert_sha256 = Strong; package_name = Weak; domain/ip/url =
Weak-and-decaying.
Corroboration count: independent sources asserting the indicator.
Freshness: age vs. expiresAt.
Contextual ﬁndings: Thraksha's own permission/proﬁle analysis and network evidence.
Decision bands (feed PolicyEngine, don't replace it):

KNOWN THREAT MATCH →  exact apk_sha256 match to a High-trust, non-expired indicator, OR a vetted
malicious cert_sha256 match not on the debug/test allowlist. Eligible for Device Owner containment
(subject to Advice Mode / user policy).
HIGH-CONFIDENCE IOC MATCH →  a strong network IOC that is fresh AND corroborated by ≥2 sources,

SUSPICIOUS / REVIEW →  weak single-source match (package name, stale IP, low submitter conﬁdence)

This structurally prevents the "one random feed says bad →  auto-quarantine" failure: containment requires a
Strong indicator type from a High-trust source.
Staleness / Expiration Policy
Set expiresAt at ingestion by type:
apk_sha256: long-lived — 24 months or non-expiring (historical artifacts stay valid); re-aﬃrm on re-
sighting.
cert_sha256 (malicious signer): long-lived — 12–24 months (campaign keys persist), but auto-revokeimmediately if the cert is a known-leaked platform cert that vendors have rotated.
domain: 3–6 months.
ipv4/ipv6/ip_port: 30–90 days (align with abuse.ch's 30-day IP RPZ / 6-month IOC window; prefer the
shorter end).
url: 30–90 days, and downgrade when URLhaus marks it oﬄine.
package_name: never authoritative; 6 months and only as corroboration.
Expired indicators are disabled for matching (enabled=false) but retained for audit/history.
Safe Investor Demo Dataset
Composition (metadata/IOCs only, no binaries), a small curated pack:
1,500–3,000 APK SHA-256 hashes (MalwareBazaar apk signature/tag exports, family-labeled).
200–500 malicious signing-certiﬁcate ﬁngerprints (CSCB + Android-relevant certs).
1,000–2,000 domains/IPs/URLs from ThreatFox apk.* families + URLhaus (fresh, non-expired).
100–300 package-name corroboration entries (low-trust, tagged).
1 clearly-labeled VillainCaller controlled indicator for the deterministic detection demo.
Total on the order of a few thousand indicators — well under 1 MB in compact form.
Why this is defensible: every indicator is traceable to a named reputable source (sourceReference), none is
fabricated, no malware binary is present, and the scanner logic is identical whether it hits demo or real data.
The truthful claim "Thraksha is scanning real installed apps against real-world threat intelligence from
abuse.ch" holds because the corpus is genuinely sourced, the hashes/certs are real, and the match engine is
the production engine.
Demo choreography (per the locked constraint):
1. Scan real installed apps on the S20 FE / Z Flip4.
2. Compute real base-APK SHA-256 and signer cert SHA-256; compare against the corpus.
3. Honestly report zero known matches if the device is clean — demonstrating integrity and a working
negative path.
4. Separately trigger the controlled VillainCaller indicator to show a KNOWN THREAT MATCH →
PolicyEngine →  Advice/containment ﬂow end-to-end.
5. Show the audit log proving the same engine used the real corpus for both.
This is more credible than planting malware because investors see an honest true-negative (the hard part
any real scanner must get right) and a controlled true-positive, with no theatrics or fabricated infection.

Production Intelligence Pipeline (FUTURE PHASE — design only)
External sources (abuse.ch APIs/exports, licensed feeds) →  ingestion (scheduled pull, per-
source rate limits + Auth-Key) →  provenance validation (record source, signature, fetch
time) →  schema normalization →  deduplication/merge (natural key, source list) →  confidence
calculation (trust × type × corroboration × freshness) →  expiration/revocation (per-type TTL,
kill list) →  Thraksha intelligence DB (server-side; PostgreSQL/MISP) →  compact mobile
ThreatPack generation (subset, binary/SQLite) →  cryptographic signing →  secure distribution
(HTTPS + pinning) →  device signature verification →  atomic activation →  rollback to last
known-good →  audit update.
STIX/TAXII vs MISP on the backend: MISP is the pragmatic hub — abuse.ch already publishes MISP feeds, it
handles dedup/correlation/expiry, and it exports normalized data. STIX/TAXII is worth supporting only if you
later ingest CISA AIS or enterprise partners; note abuse.ch deliberately dropped STIX/TAXII for size reasons.
AbuseThe mobile device should NOT receive STIX or MISP JSON — it should receive Thraksha's compact
signed format. Keep the rich standards on the backend; ship a lean derived pack.
Secure Update / Signing Architecture (FUTURE PHASE — design only)
Thraksha already veriﬁes RSA-signed packs. Harden the supply chain with:
Two-tier key hierarchy: an oﬄine root key (air-gapped, signs a rotating signing key/certiﬁcate) and an
online signing key (signs each pack). Compromise of the online key is recoverable by root-signing a new
one and revoking the old.
Version monotonicity: each pack carries a strictly increasing version + build timestamp; the device
rejects any pack with version ≤ the active version (rollback prevention).
Expiry: packs carry a notAfter; an expired pack triggers a fetch and, if oﬄine too long, a degraded
"stale intelligence" state rather than silent trust.
Emergency revocation / kill switch: a signed revocation list can disable speciﬁc indicatorIds or an
entire bad pack version; the device honors it before matching (defends against poisoned indicators and
mass false-positives).
Staged activation: verify signature →  verify version monotonicity →  verify expiry →  stage →  atomically
switch →  keep the previous pack for one-tap rollback.
Provenance in-pack: each indicator retains source/sourceReference so a bad source can be
surgically purged.
Anti-mass-quarantine safeguard: cap the number of new containment-eligible matches a single pack
update may trigger without user conﬁrmation; require the KNOWN-THREAT tier for any automated
containment.
Performance / On-Device Storage Strategy
Targets: Galaxy S20 FE (6 GB RAM, Snapdragon 865, Android 13 — the ﬂoor) and Z Flip4 (8 GB, SD 8+ Gen 1).
For a few-thousand-indicator demo pack and even a production pack of low-hundreds-of-thousands of
indicators, all approaches are cheap; choose by access pattern:
JSON: ﬁne for the tiny signed demo pack (human-auditable, trivially parsed). Poor for large sets (parse
time, memory).
SQLite: recommended production on-device store — indexed exact-match lookups on 64-char hex are
effectively constant-time at these sizes, support incremental updates, use low RAM, and are native toAndroid.
Bloom ﬁlter: ideal front ﬁlter for hash/cert set-membership — a compact bit array gives sub-microsecond
"deﬁnitely not present" answers with no false negatives, backed by SQLite for the deﬁnitive check on a
possible hit. (Forensic tooling reports dropping hash-DB lookup time from ~55 s to ~0 s by adding a
Bloom pre-ﬁlter.) This keeps per-app scan cost negligible even for hundreds of thousands of hashes.
--- PAGE 9 ---
Hash set/index (in-memory): ﬁne for the small demo pack loaded once at startup.
Binary format / segmented packs: for production, ship a compact binary + a Bloom ﬁlter, segmented by
indicator type so short-TTL IP/URL segments can update independently of long-lived hash/cert
segments (smaller incremental downloads).
Recommended path: demo = signed JSON (or SQLite) + in-memory index; production = Bloom ﬁlter front
+ SQLite backing store, segmented, incrementally updated. Do not prematurely optimize the demo.
Risks and Failure Modes
Licensing/redistribution overreach (shipping abuse.ch data commercially without a Spamhaus
arrangement) — the top risk; gate the commercial build on written permission.
Compromised/poisoned feed — mitigated by source trust tiers, corroboration requirements, and the kill
