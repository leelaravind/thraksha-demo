# PHASE 12A — MANIFEST, PERMISSION AND EXPORTED-COMPONENT AUDIT

Audited against the **merged manifest extracted from the release APK itself**
(`aapt2 dump xmltree`), not the source manifest. Raw dump: `merged_manifest_release.txt`.

| # | Permission | Class | Why it is there |

| --- | --- | --- | --- |

## 4. OPEN DECISION — package visibility for the private alpha

This is the one substantive judgement 12A cannot make on the owner's behalf.

**Measured, same device, minutes apart:**

| | debug | release candidate |
| --- | --- | --- |
| Packages analysed | 441 | **322** |
| Third-party user apps | ~119 | **0** (only the 2 declared demo packages) |
| Reported scope | FULL | **REDUCED**, stated in the UI |

The release candidate can see every *system* package and the two demo packages, but **none
of the user's actually-installed third-party apps** — the ones a private alpha would most
want scanned.

The app is honest about it, so nothing is misrepresented. But the owner should choose
knowingly between:

* **Option A — ship as-is (current state).** Least privilege; no broad-visibility
  permission. The scanner is largely limited to system packages on a personal phone, so
  the Protect surface delivers much less than the demo suggested. Automation, Ask
  Thraksha, Network Guard and Audit are entirely unaffected.
* **Option B — add `QUERY_ALL_PACKAGES` to the main manifest.** Restores the 441-package
  reach demonstrated in Phase 11B. Google Play restricts this permission to declared,
  permitted use cases — device security/anti-malware is one of them — so it is defensible
  in principle, but it broadens the permission surface and would need a Play declaration
  if the app were ever published.

**12A does not make this change.** Adding a broad permission is a scoping decision with
policy implications, not a defect fix, and the guide's §7 instruction is to remove
unnecessary permissions on evidence — not to add them silently. Recorded for the owner as a
HIGH-visibility item in the 12C risk register.

## 5. `ThrakshaAccessibilityService` — recommended for removal (not removed here)

Phase 11B established that **automation does not use the Accessibility Service**: routines
work through Notification Policy access and Modify System Settings. The service survives
only as a developer probe reachable from Settings → Developer diagnostics.

Shipping it has real costs: an AccessibilityService is the most privileged surface a normal
Android app can declare, it triggers Play policy review, and it invites the exact
misunderstanding Phase 11B removed from the UI (Stitch had invented an "Accessibility
required" onboarding screen, which was rejected).

It is **not removed in this candidate** because deleting a manifest service plus its
diagnostics call-sites is a functional change to a frozen build, and 12A's remit is to
audit and minimally fix. The manifest already declares
`isAccessibilityTool=false`, and the service is inert unless the user enables it manually
in Android settings — which the private-alpha instructions do not ask them to do.

**Recommendation:** remove the service, its config XML and its diagnostics call-sites
before any distribution beyond the owner. Logged as MEDIUM in the 12C register.
